Prompt Promotion is the B1 workflow that lets you move prompt versions from
`staging` to `production` through automated eval checks, with drift-based
rollback when the post-promotion metrics **you post** regress. Rollback is not
autonomous — see [Auto-rollback](#auto-rollback) for exactly what fires it.

**Pricing:** Read-only (view active version + history) on **Builder $59**.
Full promotion workflow — create, gate, promote, drift-based rollback — on **Team $249+**.

## Core concepts

| Concept | Description |
|---|---|
| **Prompt** | A named template managed by Tracelane (`/v1/prompts/:name`) |
| **Version** | An immutable snapshot of a prompt's content, SHA-256 hashed |
| **Environment** | `staging`, `canary`, or `production` |
| **Eval gate** | A set of eval assertions that must pass before promotion |
| **Auto-rollback** | Revert when a metric **you post** drifts past a σ threshold post-promotion. Gateway traffic updates the drift baseline but cannot trigger a revert |

```
  Author a new version
        │
        ▼
  Deploy to staging
        │
        ▼
  Eval gate runs (all assertions must be green)
        │ pass          │ fail
        ▼               ▼
  Promote to        Blocked — fix
  production        the prompt
        │
        ▼
  POST your metrics to /v1/prompts/:name/observe
  (cost, latency, guardrail-fire rate, eval score)
        │ drifts > threshold
        ▼
  Rollback fires → previous version restored
```

## Create and version prompts

Versions are authored through the API (or the **Prompts** page in the dashboard).
A new version is created and lands in `staging`:

```bash
curl -X POST https://gateway.tracelane.dev/v1/prompts/my-agent-system/versions \
  -H "Authorization: Bearer tlane_..." \
  -H "Content-Type: application/json" \
  -d '{
    "content": "You are a helpful assistant...",
    "model_pin": "claude-sonnet-4-6"
  }'
```

The `201` response carries the `prompt_version_id` and the content `sha256_hex` —
the id you pass to promote and rollback.

The `tlane` CLI covers the read and promotion side of the workflow:

```bash
tlane prompt list my-agent-system      # promotion + rollback history
tlane prompt show my-agent-system      # active version per environment
tlane prompt diff my-agent-system --from-env staging --to-env production
```

## Eval gates

<Note>
**Eval gating is live.** Run a suite with `POST /v1/prompts/{name}/evals`, then pass
the returned `eval_run_id` to `promote`: a run recorded `passed` opens the gate, and
anything else — `failed`, `errored`, still `running`, or an id the gate cannot
resolve — refuses the promotion with `409` and leaves the production pointer where it
was. **The gate fails closed**, so an unreadable run blocks rather than waves through.

Still on the roadmap: the `tracelane.yaml` gate config and the streaming eval panel.
Assertions are code rules plus an optional LLM judge — see
[Evals and prompt promotion](/eval-gates). And a promotion is never gated
*automatically* — you choose to supply a run id, or to record an attributed override
instead.
</Note>

Eval gating is live. A staging → production promotion requires a passing eval
run; without one the non-override path returns `409`. Start a run with
`POST /v1/prompts/{name}/evals`. Declarative per-prompt thresholds in
`tracelane.yaml` are still roadmap:

```yaml
# Roadmap: declarative thresholds have no reader in the current gateway.
# The gate itself is live via POST /v1/prompts/{name}/evals.
prompts:
  my-agent-system:
    eval_gate:
      suite: evals/smoke/
      pass_threshold: 1.0      # 100% of assertions must pass
      timeout_seconds: 120
    auto_rollback:
      metric: eval_score
      window_minutes: 30
      sigma_threshold: 2.0
```

The eval suite referenced here is the same format as the CI merge-gate suite.
See [Eval gates](/eval-gates).

## Promote via dashboard

1. Open **Prompts → [prompt name]**.
2. The panel shows the active version for each environment.
3. Click **Promote staging → production**.
4. The version is atomically swapped in production and a **tamper-evident
   promotion record** is written. _(The **panel** does not run or stream an eval
   yet, so a promotion made from this button is a recorded manual-override. The
   gate itself is live over the API — supply an `eval_run_id` to `promote` and a
   non-passing run refuses with `409`. Streaming it into the panel is V1.1.)_

## Promote via API

Promote against the **gateway**, not the dashboard origin. The dashboard route
authenticates with a WorkOS session **cookie** and ignores an `Authorization`
header; the gateway takes a Bearer credential.

`to_version_id` is **required** and is a UUID — get it from the `201` body of
`POST /v1/prompts/{name}/versions`, or from `GET /v1/prompts/{name}`.

```bash
curl -X POST https://gateway.tracelane.dev/v1/prompts/my-agent-system/promote \
  -H "Authorization: Bearer $TRACELANE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "from_env": "staging",
    "to_env": "production",
    "to_version_id": "3f1a6c2e-9b04-4d77-8a51-2e0c7f9b1d43",
    "override_reason": "Better refusal rate on the jailbreak suite"
  }'
```

<Note>
  `override_reason` is shown instead of `eval_run_id` because **nothing produces
  eval runs yet** — supplying an `eval_run_id` returns `409` today. The override
  path records an explicit, attributed bypass in the tamper-evident chain, which
  is the honest way to promote until eval runs exist. The key needs the `admin`
  scope; keys minted before scoping (`scope` unset) are unaffected.
</Note>

Response on success — every id is a UUID:

```json
{
  "promotion_id": "0f9c1a77-5b2d-4e18-9a30-6c5f8b2e4d91",
  "from_version_id": "1c8b4e60-2a97-4f33-b5d2-70a1e9c6f382",
  "to_version_id": "3f1a6c2e-9b04-4d77-8a51-2e0c7f9b1d43",
  "from_env": "staging",
  "to_env": "production",
  "eval_run_id": null,
  "decision": "manual_override",
  "notes": "manual override: user override by user_01H…: Better refusal rate on the jailbreak suite"
}
```

If you supply an `eval_run_id` instead of an `override_reason`, the gate
resolves it and **blocks** — `409 Conflict`, and the routing pointer does not
move. This is the shape you get today, and it is what makes an `eval_run_id`
unusable until eval runs are produced: the gate cannot find the run, and a gate
that cannot resolve its run fails **closed**.

```json
{
  "promotion_id": "0f9c1a77-5b2d-4e18-9a30-6c5f8b2e4d91",
  "from_version_id": null,
  "to_version_id": "3f1a6c2e-9b04-4d77-8a51-2e0c7f9b1d43",
  "from_env": "staging",
  "to_env": "production",
  "eval_run_id": "8d2f5b91-3c47-4a06-9e18-b7d0f6a2c845",
  "decision": "blocked_by_eval",
  "notes": "blocked: eval gate failed for run 8d2f5b91-3c47-4a06-9e18-b7d0f6a2c845"
}
```

Omitting `eval_run_id` **and** `override_reason` returns `409` with
`"decision": "blocked_by_policy"`.

## Auto-rollback

<Note>
**How it works today:** rollback decisions are computed from metric observations
**you report** to the observe endpoint. When you post an observation, Tracelane
compares it to the pre-promotion baseline and, if it drifts more than
`sigma_threshold` standard deviations within the observation window, returns a
rollback decision (and reverts, under `rollback_mode: auto`). **Autonomous
background monitoring** — Tracelane firing a rollback with no observation pushed
to it — is on the **V1.1 roadmap**; today the drift math runs on the observations
you feed it, not on a standalone monitor loop.
</Note>

When an observation drifts more than `sigma_threshold` standard deviations from
the pre-promotion baseline within the observation window, the rollback fires per
`rollback_mode`.

| `rollback_mode` | What happens |
|---|---|
| `auto` | Reverted immediately without human input |
| `suggested` | Dashboard shows a rollback suggestion; human confirms |
| `human_confirmed` | Suggestion was accepted |
| `dismissed` | Suggestion was dismissed |

The history entry on the prompt detail page shows the trigger metric, observed
value, sigma drift, and the version pair:

```
Auto-rollback fired (eval_score)  — 2.3σ drift, value 0.71 — v→a3b2c1 from v→d4e5f6
```

## Canary splits (Team+) — roadmap (V1.1)

<Warning>
**Not yet shipped.** Prompt-version traffic splitting — routing a percentage of
requests to a candidate version — is on the V1.1 roadmap. There is no
`traffic_pct` splitter in the current gateway. A `canary` **environment pointer**
exists (you can pin and read a `canary` version), but traffic is **not** split by
percentage today; promote/rollback operate on the full environment.
</Warning>

When it ships, you will route a percentage of traffic to a candidate version
before full promotion:

```yaml
# V1.1 (roadmap) — no traffic_pct splitter in the current gateway.
prompts:
  my-agent-system:
    canary:
      version_id: v_new
      traffic_pct: 10     # 10% → canary, 90% → production
      min_requests: 500   # don't evaluate until enough data
```

After sufficient traffic, you will promote the canary to production via the same
promote endpoint with `from_env: "canary"`.

## Read the active version from your agent

```python
import httpx

res = httpx.get(
    "https://gateway.tracelane.dev/v1/prompts/my-agent-system",
    params={"env": "production"},
    headers={"Authorization": f"Bearer {api_key}"},
)
prompt = res.json()["content"]
```

```typescript
const res = await fetch(`${GATEWAY_URL}/v1/prompts/my-agent-system?env=production`, {
  headers: { Authorization: `Bearer ${apiKey}` },
});
const { content } = await res.json();
```

The gateway caches prompt versions in memory — the hot path latency to resolve
a prompt is `<1ms` p95.

## Audit trail

Every promotion, block, and rollback is written to the tamper-evident audit
ledger with the version SHA-256, eval run ID, and actor. Use `tlane verify`
to confirm the log has not been altered.
